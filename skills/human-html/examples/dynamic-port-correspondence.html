In plain terms

  • What changed: the token bucket that admits or throttles every request on the edge gateway now exists twice: crates/quota/src/bucket.rs (shipping) and packages/quota/src/bucket.ts (the port for the Node gateway). Nothing about the limits themselves moved: same capacity of 600 per key, same refill of 5 tokens per second.
  • Where it stands: eight regions of the file carry a behavioural trap. Four are preserved exactly, four are changed on purpose, and every one of the four changes replaces a compiler guarantee with a convention plus one test.
  • What the sign-off needs: a yes on the eight numbered notes, then a yes on the ledger and on the edge-case verdicts. The parity harness replayed 41,208 recorded (timestamp, cost) pairs from an hour of production traffic on 2026-07-24 and every admission decision and every Retry-After value matched, which is evidence for the four preserved regions and says nothing about the four changed ones.

The short version: the port is mergeable, and the part worth arguing about is note 4, where an over-capacity bucket stops crashing and starts being quietly repaired.

What the refill loop does

The bucket stores no fractional tokens. It stores a whole-token count and one timestamp, and the leftover time between whole tokens survives by not being consumed: when a refill mints nothing, the timestamp stays where it was, so the next call sees the full accumulated gap. That single line is where the rate lives, and it is the line a rewrite is most likely to tidy away.

How the numbered marks work

The two panels below hold the same 60-line function in two languages. Corresponding regions are highlighted and carry the same number, and that number is a link to the note that explains what the region does and what breaks if it is written the obvious way instead. Note 4 in the Rust panel and note 4 in the TypeScript panel are the same claim about the same behaviour; each note links back to both marks.

Numbers and notes carry the whole relationship. Nothing here depends on colour, on a pointer, or on JavaScript: the pairing survives a print-out, a greyscale copy, and a JavaScript-disabled preview. Each numbered link is a tab stop, and reaching one by keyboard or hovering its region brightens the counterpart in the other panel, because the highlight listens on the region and focus events bubble up from the link inside it. That brightening is decoration on top of the numbers, so losing it costs nothing.

pub struct Bucket {
    capacity: u32,
    refill_per_sec: u32,
    tokens: u32,
    last_refill: Instant,
}

impl Bucket {
    /// Caller holds the shard lock for the whole call.1
    pub fn try_take(&mut self, now: Instant, cost: u322) -> Outcome {
        self.refill(now);
        if self.tokens >= cost3 {
            self.tokens -= cost;
            Outcome::Allowed { remaining: self.tokens }
        } else {
            Outcome::Throttled { secs: self.retry_after_secs(cost) }
        }
    }

    fn refill(&mut self, now: Instant) {
        let elapsed = now.saturating_duration_since(self.last_refill)5;
        let minted = (elapsed.as_nanos() as u64)
            .saturating_mul(self.refill_per_sec as u64)
            / 1_000_000_0006;
        if minted == 0 {
            return;
        }7
        let headroom = (self.capacity - self.tokens) as u644;
        self.tokens += minted.min(headroom) as u32;
        self.last_refill = now;
    }

    fn retry_after_secs(&self, cost: u32) -> u64 {
        let deficit = (cost - self.tokens) as u64;
        deficit.div_ceil(self.refill_per_sec as u64).max(1)8
    }
}

Port · packages/quota/src/bucket.ts 28-88

export class Bucket {
  private tokens: number;
  private lastRefillMs: number;

  constructor(
    private readonly capacity: number,
    private readonly refillPerSec: number,
    nowMs: number,
  ) {
    this.tokens = capacity;
    this.lastRefillMs = nowMs;
  }

  /** Synchronous on purpose: no await between refill and the subtraction.1 */
  tryTake(nowMs: number, cost: number): Outcome {
    if (!Number.isInteger(cost) || cost < 1) throw new BadCost(cost);2
    this.refill(nowMs);
    if (this.tokens >= cost3) {
      this.tokens -= cost;
      return { kind: "allowed", remaining: this.tokens };
    }
    return { kind: "throttled", secs: this.retryAfterSecs(cost) };
  }

  private refill(nowMs: number): void {
    const elapsedMs = Math.max(0, nowMs - this.lastRefillMs)5;
    const minted = Math.floor((elapsedMs * this.refillPerSec) / 1000)6;
    if (minted === 0) {
      return;
    }7
    const headroom = Math.max(0, this.capacity - this.tokens)4;
    this.tokens += Math.min(minted, headroom);
    this.lastRefillMs = nowMs;
  }

  private retryAfterSecs(cost: number): number {
    const deficit = cost - this.tokens;
    return Math.max(1, Math.ceil(deficit / this.refillPerSec));8
  }
}

Every line outside a mark is a mechanical transcription: same order, same names, same structure, nothing to check. The one thing on the right with no counterpart on the left is the constructor, because Bucket::new sits above line 41 and sets the same two fields the same way. The eight marks are the whole review surface.

The eight notes

1
Refill and take have to stay one uninterrupted step.

Rust takes the shard lock in the caller and holds it across the whole of try_take, so no other request can observe the bucket between the refill and the subtraction. The port has no lock and needs none while tryTake stays synchronous, because the event loop cannot interleave another request inside a function with no await in it.

The failure is one await away. Put await store.load(key) between this.refill(nowMs) and the subtraction and two requests arriving in the same tick both read tokens === 1, both come back allowed, and a key capped at 600 admits 601 with nothing in the metrics to show it. bucket.parity.test.ts asserts that tryTake(...) is not a promise, which catches that edit and would not catch a later split of the method in two.

Marked at bucket.rs and bucket.ts.

2
u32 rejected a fractional or negative cost before the function ran; number does not.

In Rust the two call sites pass a compile-time 1 or 5 and the type refuses everything else. In the port the cost arrives from a request body. A body of {"cost": 0.5} would pass this.tokens >= cost, subtract 0.5, and leave the bucket on a fractional count it can never return from, so X-RateLimit-Remaining reports 599 while the admission arithmetic runs on 599.5. A body of {"cost": -3} would add three tokens.

The guard is the port's replacement for the type, and it rejects with 400 rather than rounding, because a caller sending 0.5 has a bug worth surfacing.

Marked at bucket.rs and bucket.ts.

3
The comparison is inclusive, and the last token is spendable.

Writing > instead refuses the request that spends the last token: a client sending a burst of exactly 600 against a capacity of 600 gets 599 through and one 429 that the shipping build never sends. A soak test averages that away; a nightly batch job that sizes its burst to the documented limit hits it every run.

Marked at bucket.rs and bucket.ts.

4
An over-capacity bucket stops growing instead of crashing, and is not repaired.

In Rust, (self.capacity - self.tokens) is u32 subtraction. If tokens ever exceeded capacity a debug build panics on that line and a release build wraps to a headroom near 2^32, which is the broken invariant made loud. The port clamps the headroom at zero with Math.max(0, ...), so refill adds nothing while the bucket is over capacity.

Clamping the headroom is not the same as clamping the bucket, and it is worth being exact about which one this is. On a downgrade from 600 to 100 with 600 tokens held, headroom is 0 and this.tokens += Math.min(minted, 0) leaves 600 in place. The bucket does not come back under 100 on its own; it only falls as callers spend, so the downgraded tier keeps serving up to 600 of the old allowance before the new cap starts to bite. Nothing in this file notices.

The only way tokens can exceed capacity is a capacity that shrank under a live bucket, for example a tier downgrade applied by config reload. The shipping build puts that in a crash log within one refill; the port absorbs it in silence and keeps serving. That is the one change here worth arguing about, and the compensation is not in this file: packages/quota/src/store.ts logs at warn level when a reload lowers a capacity under a bucket that is above it. A log line is weaker than a panic, and it does not bound the over-serving.

Marked at bucket.rs and bucket.ts.

5
Instant cannot go backwards; the port's clock can, and the clamp is what makes that safe.

Rust reads a monotonic Instant, so saturating_duration_since is effectively dead code there. The port takes nowMs from performance.now(), passed in by the caller, and clamps with Math.max(0, ...) because the clamp stops being dead code the moment somebody swaps that caller to Date.now(): an NTP correction that steps the wall clock back 1.2 s makes elapsedMs negative, minted negative, and the bucket loses 6 tokens that no request spent.

Milliseconds instead of nanoseconds is the other half of this change. At the ceiling tier of 5,000 tokens per second, elapsedMs * this.refillPerSec stays under 2^53 for any process uptime below roughly 57 years, so the wider integer buys nothing here.

Marked at bucket.rs and bucket.ts.

6
Integer division truncates in Rust, so the port needs Math.floor to match.

Drop the floor and a 50 ms gap at 5 tokens per second mints 0.25 instead of 0. That looks harmless and is not: the zero check in note 7 never fires again, the timestamp advances on every call, and the refill rate starts depending on how often the bucket is polled. This is the single most attractive simplification in the file.

Marked at bucket.rs and bucket.ts.

7
When nothing is minted the timestamp must not move: this is where the remainder is kept.

There is no fractional token field, so the leftover time lives in last_refill by not being consumed. A client polling every 50 ms at 5 tokens per second mints nothing on any single call and mints 1 on every fourth, which is exactly the configured rate.

Advance the timestamp on the zero path and that client never accrues a token at all: each call truncates 0.25 to 0 and resets the window, so after its opening burst it stays throttled for as long as it keeps polling at 20 requests per second. The two tracks in What the refill loop does are this note.

Marked at bucket.rs and bucket.ts.

8
Round the wait up, and never put a zero on the wire.

Retry-After is whole seconds, so rounding down under-reports the wait. Use Math.round here and a deficit of 1 token at 5 per second gives round(0.2), which is 0, and a client backoff library reads Retry-After: 0 as retry immediately: one throttled request becomes a hot loop of roughly 300 requests per second against the same bucket, every one of them throttled.

The max(1) is belt and braces carried over from the Rust side. With an integer cost the deficit is at least 1, so the ceiling already guarantees at least 1 second; the floor only starts earning its place if a fractional cost is ever allowed through note 2.

Marked at bucket.rs and bucket.ts.

Four of the eight notes (3, 6, 7, 8) say the port copied the shipping behaviour and the arithmetic backs that up; the other four (1, 2, 4, 5) each swap a language guarantee for a convention, which is what the ledger below is for. Note 4 is the one region that lands on both sides of that split, so it is cited twice in the ledger: the headroom clamp is copied, and only the behaviour on an over-capacity bucket changed.

Behaviour ledger

Three columns: what came across untouched, what changed on purpose, and what was dropped because the hazard it guarded against does not exist in the port.

Preserved exactly

  • Truncating refill, paired with the zero-mint early return that keeps the remainder in the timestamp (notes 6, 7).
  • The headroom clamp, so 6 hours idle mints 600 tokens and not 108,000 (the copied half of note 4).
  • tokens >= cost, inclusive, so the last token is spendable (note 3).
  • Retry-After in whole seconds, rounded up, never below 1 (note 8).

These four are the rate, and each one can be undone by an edit that looks like tidying up.

Deliberately changed

  • Instant nanoseconds becomes performance.now() milliseconds, with the backwards-clock clamp kept and now load-bearing (note 5).
  • Mutex<HashMap<Key, Bucket>> becomes plain fields; atomicity comes from a synchronous-only rule plus one test (note 1).
  • A runtime cost guard stands in for what u32 used to refuse (note 2).
  • An over-capacity bucket stops refilling rather than panicking, and keeps serving its old allowance down (note 4).

Each of the four trades a compiler or runtime guarantee for a convention, and each convention has exactly one test holding it up.

Dropped, not needed

  • saturating_mul on the mint: in milliseconds the product cannot overflow a JavaScript number for any uptime that matters (note 5).
  • Send and Sync impls and the Arc wrapper: one event loop, nothing to share across threads.
  • The Duration wrapper on the retry value: both call sites want whole seconds, so the port returns a number.

None of the three can change an admission decision; each guarded a hazard that the port does not have.

Read the middle column as the sign-off surface: the left column is checked by the replay harness and the right column has nothing left to check.

Four rows are the same computation and four reach the same answer by different means, which means half the table has to be rechecked whenever a call site changes and half does not.

a. What "equivalent" claims, and what "identical" claims that it does not. identical means the two builds run the same steps on the same inputs and produce the same value: swapping one for the other changes nothing a caller or a test can observe. equivalent is the weaker claim, and every use of it above is bounded: the same decision reached by different means, for every input this gateway can actually produce. The cost-of-0 row is equivalent only because the two Rust call sites pass a compile-time constant; a third call site passing a variable would turn that row into a real difference. An equivalent verdict is a statement about the current call sites, so it expires when they change, and an identical one does not.

What this does not cover

  • The replay harness ran single-threaded against recorded timestamps, so nothing in the 41,208 pairs exercises two requests racing for the last token. Note 1 rests on one test that fails if tryTake returns a promise, and that test would not notice the method being split in two with an await between the halves.
  • The cross-instance limit path is untouched: crates/quota/src/shared.rs has no port yet, and every number here is per-process. A key that hits two gateway instances still gets two buckets, in both builds.
  • The performance.now() origin resets when a worker restarts, and buckets live in process memory, so a restart hands every key a full bucket. The shipping build does the same on redeploy, so this is parity rather than a fix, and note 5 stops holding at all if buckets are ever moved to a store that outlives the process.
  • Not measured: what the Number.isInteger guard costs on the hot path. It runs once per request and is very likely free, and no number in this artifact says so.

Three of those four are scope, and the first is the one that could hide a real defect.

On balance the port is worth merging on the strength of the replay plus the eight notes, with note 4 flagged for a second opinion, and shared.rs is the file that still needs the same treatment before the Node gateway can take production traffic.
